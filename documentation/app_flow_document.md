# App Flow Document for the Faculty Survey Application

## Onboarding and Sign-In/Sign-Up
A new user arrives at the application by navigating to the public landing page in their browser. Respondents see a simple welcome screen that lists available surveys without any login requirement. Administrators access the same URL and choose the “Admin Login” link in the top header. Clicking this link takes them to the sign-in page where they can enter their email address and password. The application uses an email/password scheme backed by Better Auth, and environment variables securely hold secrets such as the authentication keys. If an administrator has forgotten their password, they click a “Forgot Password” link which prompts them to enter their email address. The system then sends a password reset email containing a secure, time-limited link. Upon following that link, the admin can choose a new password and is redirected back to the sign-in screen. After successful sign-in, a session cookie is created and the user is redirected to the main dashboard. Signing out is as simple as clicking a “Sign Out” button in the header, which clears the session cookie and returns the user to the public landing page.

## Main Dashboard or Home Page
Once an administrator has signed in, they arrive at the main dashboard located at `/dashboard`. The top of the page features a header with the application logo on the left, the current user’s name in the middle, and a sign-out button on the right. A collapsible sidebar along the left edge provides navigation links to all major admin sections: “Questionnaires,” “Reports,” and “Admin Management.” The central area displays a summary widget that shows recent survey activity, such as how many surveys have been completed in the last week. All UI elements use Tailwind CSS for styling and shadcn/ui components for consistent look and feel. The respondent landing page, by contrast, simply shows a grid of available surveys with a call-to-action button to begin each survey.

## Detailed Feature Flows and Page Transitions
When an administrator wants to create a new questionnaire, they click the “Questionnaires” link in the sidebar. This loads a page at `/dashboard/questionnaires` that lists all existing questionnaires in a data table. To add a new one, the admin clicks a “New Questionnaire” button located above the table. That action opens an in-page form built with shadcn/ui input components for title, description, and question definitions. Each question can be configured as multiple choice or open-ended text by selecting a radio-style toggle. Upon submitting the form, a Next.js Server Action is invoked. The server application validates the input with Zod, then uses Drizzle ORM to insert the new questionnaire and its questions into the PostgreSQL database. The page refreshes the list to include the newly created entry.

Editing an existing questionnaire is achieved by clicking an “Edit” icon in the row of the questionnaire list. This navigates to `/dashboard/questionnaires/[id]/edit`, where a form prepopulated with the current values appears. After making changes and saving, the system updates the database via another Server Action and navigates back to the list view.

For respondents, clicking a survey on the public landing page navigates them to `/survei/[id]`. The survey page dynamically fetches questions for that questionnaire from the server. Respondents fill out form fields, and upon clicking “Submit,” a Server Action checks whether the respondent has already submitted answers for that survey. If not, it stores the new responses in the `Jawaban` table and displays a confirmation message. If they have already responded, an alert appears to explain that only one submission is allowed.

Administration of other admins is done by clicking the “Admin Management” link in the sidebar. This page at `/dashboard/admins` lists all administrator accounts. Super-admins see an “Invite Admin” button, which opens a form to send an email invitation. Accepting the invitation leads new admins through a special sign-up flow, where they set their password before landing on the main dashboard. Deletion and role changes occur via in-line actions in the administrators’ table, each triggering a Server Action and a page refresh.

Viewing reports is handled under the “Reports” link in the sidebar. That page at `/dashboard/reports` shows a list of completed surveys. Clicking a specific survey name loads `/dashboard/reports/[id]`, where aggregated results appear in tables and charts. The application uses Chart.js to render bar and pie charts. For open-ended responses, there is a “Generate AI Summary” button that calls a custom API route at `/api/gemini` with the text answers. The route securely forwards the content to the Gemini API and returns a concise summary, which is then displayed beneath the charts. Administrators can click “Export as PDF” to generate a report document on the client side using jsPDF and html2canvas.

## Settings and Account Management
Administrators access their personal settings by clicking their user name in the header and choosing “Profile.” This navigates to `/dashboard/profile`, where they can update their display name, email address, and change their password. Any changes are submitted through a Server Action that updates the users table via Drizzle ORM. Notification preferences for new survey alerts can be toggled in this same screen. After saving, a confirmation toast appears, and the user can click a link to return to the dashboard or immediately navigate to any other section via the sidebar.

## Error States and Alternate Paths
If a user submits invalid data in any form—such as leaving required fields blank or entering text that is too long—the UI displays inline error messages in red text beneath the relevant input fields. Server-side validation errors return structured feedback that the UI maps to these inline messages. Network failures during API calls show a banner at the top of the page indicating “Network Error, please try again.” The application retries on recoverable errors up to two times. If an administrator attempts to access a protected route like `/dashboard` without a valid session cookie, they are redirected to the sign-in page. If the Gemini API call fails or returns an error, the summary section displays a fallback message explaining that the analysis is temporarily unavailable and invites the user to reload the page.

## Conclusion and Overall App Journey
In a typical day, a new administrator signs up using an email invitation link, sets their password, and signs in via the login page. They land on the dashboard, create or edit questionnaires, and view live reports rendered with charts and AI-powered summaries. Respondents simply visit the public landing page, select an active survey, complete the form once, and receive a confirmation. Throughout all interactions, the app seamlessly transitions between pages using Next.js App Router, keeps data type-safe end to end with TypeScript and Drizzle ORM, and ensures responsive, modern styling with Tailwind CSS and shadcn/ui components. Error handling and settings management are built in so that both administration and everyday usage remain intuitive and secure.
